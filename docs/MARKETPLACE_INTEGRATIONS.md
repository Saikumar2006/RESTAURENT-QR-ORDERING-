# Marketplace integrations

Swiggy and Zomato are **not connected** in this deployment. The repository has provider status reporting and an adapter boundary, but no merchant/POS integration credentials, webhook secrets, sandbox access, or reviewed partner contract were provided. The setup guide intentionally does not prescribe private dashboard automation or undocumented endpoints.

The official [Zomato POS integration overview](https://www.zomato.com/developer/integration/docs/overview/) documents menu, outlet, and order-management APIs and says POS vendors must configure webhooks for order updates. Zomato's [onboarding guide](https://www.zomato.com/developer/integration/docs/getting-started/development-for-integration/pre-integration/) requires partner onboarding, API keys from the Zomato point of contact, an NDA, and whitelisting details. Its [prerequisites](https://www.zomato.com/developer/integration/docs/getting-started/prerequisites/) currently list a minimum of 50 restaurants or 10,000 monthly orders, critical feature parity, a 24/7 on-call channel, and 99.999% uptime; final eligibility is decided by Zomato. This application has not obtained acceptance or credentials, so its Zomato adapter remains disconnected.

Swiggy's official [Builders Club developer quickstart](https://mcp.swiggy.com/builders/docs/start/developer/) and [production access process](https://mcp.swiggy.com/builders/access/) describe OAuth access to consumer commerce tools with reviewed production access. Its [access and onboarding documentation](https://mcp.swiggy.com/builders/docs/operate/access/) describes seeded staging data and production rollout. These sources do not establish a restaurant-partner POS feed for ingesting a merchant's incoming Swiggy orders into a third-party POS. Do not treat consumer ordering/tracking tools as that feed. Seek the applicable merchant/POS partner agreement and webhook contract before connecting restaurant order ingestion.

Before enabling either provider, obtain acceptance and written partner access for this POS product and its restaurant tenants, plus official API/webhook documentation for the merchant. Implement the provider-specific signature verifier, payload validation, event dedupe, order upsert using `(restaurantId, source, externalOrderId)`, status transition allowlist, retries/checkpoints, and connection health endpoint. Verify inbound signing requirements and replay windows from that provider's official contract. External order state writes must remain disabled until the partner confirms the operation is supported.

The admin integration panel reports both marketplaces as `NOT_CONFIGURED` and provides manual order entry. Do not copy marketplace payments into Svaadya online checkout. After integration, preserve provider order ID and settlement metadata and reconcile delayed/duplicate webhooks in a sandbox before production. No Swiggy/Zomato sandbox verification has been performed.

## Current application status

The restaurant order inbox already filters the shared `Order` records by source/status/date, searches server-side, pages, shows details, receives Socket.IO refreshes, and supports a role-protected manual entry fallback. `Order` has a unique `(restaurantId, source, externalOrderId)` constraint plus independent `paymentMethod` and `settlementStatus` fields. The additive `20261026000001_marketplace_sync_metadata` migration adds source status/sync fields and a unique tenant/provider/event ID ledger for a future approved adapter. These fields and event records are not populated by the current disconnected adapter; there is no authorized Swiggy/Zomato merchant feed or provider webhook signature contract implemented. Do not infer live sync from the source filter options.

Restaurant Admin > **Integrations** reports the existing adapter status and provides partner onboarding steps. In development only, **Preview test fixture** returns a synthetic, normalized, read-only object marked `TEST_FIXTURE` and `persisted: false`; it is not an official provider payload and cannot create an order. Production disables this endpoint. The existing marketplace adapters continue to reject ingestion while partner authorization and documentation are absent. Manual orders remain visibly labelled `MANUAL`.

No marketplace credentials or environment variables have been added. There is no safe credential configuration flow yet: provider-specific secrets, outlet identity, webhook verification, event ID semantics, amount fields, retry behavior, and allowed status transitions must come from the approved partner contract. Do not store marketplace passwords or copy undocumented payloads into the adapter. After authorization, add the verified contract, encrypted/secrets-manager configuration, connection health, stable event dedupe and source status/sync metadata, then test delayed/out-of-order/duplicate delivery and settlement behavior in the provider sandbox. Until then, status remains `NOT_CONFIGURED` and integration is not live.
