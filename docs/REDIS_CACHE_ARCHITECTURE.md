# Redis cache architecture

Redis is optional for correctness. Public menu data and active public table choices use cache-aside with five-minute TTLs; keys use `REDIS_KEY_PREFIX` (default `svaadya:v1`) and include restaurant identity, for example `svaadya:v1:restaurant:menu:{restaurantId}:public` and `svaadya:v1:restaurant:public:tables:{restaurantId}`. Menu/category writes invalidate the restaurant menu namespace using SCAN batches; table create/update/deactivate deletes that restaurant's table key after the database write. Cache errors return to authoritative database reads. No staff, permissions, sessions, payments, or private restaurant data are cached.

Redis also supports Socket.IO pub/sub and atomic distributed fixed-window rate limits. On Redis rate-limit failure a bounded in-process limiter is used; this is degraded protection and is not globally coordinated. Cache payload JSON is parsed defensively and TTLs are bounded to 1 second–24 hours. Redis client errors are sanitized. Configurable operation timeout is applied to cache and rate-limit calls; connection timeout applies to connect.

Set server-only environment values: `REDIS_URL`, `REDIS_TLS_ENABLED` (true for TLS providers when needed), `REDIS_KEY_PREFIX`, `REDIS_CONNECT_TIMEOUT_MS`, and `REDIS_OPERATION_TIMEOUT_MS`. Redis URLs and passwords must never be placed in client/Vite variables or committed. A `rediss://` URL enables TLS through the URL; set TLS flag for providers whose URL remains `redis://` but require TLS.

Invalidation is best effort after committed writes, not an outbox. A crash between DB commit and invalidation can leave public menu/table data stale for at most the five-minute TTL. This does not affect authorization because permission checks always query the database. No single-flight lock is used; cached reads are modest public queries. Verify on staging by reading the same public menu twice, changing one menu item, and confirming the next read reflects it. Live Redis verification has not been run.
