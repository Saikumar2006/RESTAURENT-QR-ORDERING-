# Tenant isolation and security notes

Restaurant identity for authenticated routes comes from the database user record found by the signed tenant token, never from body/query role or tenant claims. Role endpoints explicitly compare the URL restaurant ID to that authenticated restaurant. Staff, table, menu, order, coupon, and analytics service queries are scoped by authenticated restaurant ID; nested menu categories are verified within that tenant. Platform auth has a distinct JWT type and database model, so a tenant token cannot enter platform routes.

Authorization is default-deny at guarded endpoints and resolves active user + current role permissions per request. Legacy ADMIN maps to OWNER; ordinary legacy users get limited STAFF permissions. Public QR/menu/order flows remain public by design and use public slug/table tokens rather than exposing private staff data. Cache keys include restaurant identity; authorization results are not cached.

Audit entries are written transactionally with staff and role changes and are exposed only via the tenant audit read permission. The current schema does not provide immutable/WORM audit storage, correlation IDs on audit rows, failed authorization event persistence, or platform support access auditing. Staff account deactivation is checked on each authenticated request, immediately invalidating that account's bearer token; there is no refresh token/session table to revoke.

The model has one restaurant per user and does not currently support assigned waiters, financial platform roles, support impersonation, refunds, or a final-owner transfer workflow. Final existing OWNER records cannot be changed from this staff controller, but no dedicated transfer workflow exists. Tenant negative endpoint tests against two database fixtures and external services are not available in this checkout; existing automated tests cover permission resolution and middleware behavior, not a full cross-tenant integration matrix.
