# WhatsApp customer OTP

The checkout already uses Meta's WhatsApp Business Cloud API template send and a separate OTP service. OTPs are generated with cryptographic randomness, stored as keyed HMACs, expire after five minutes, have attempt/resend limits, invalidate prior codes, and are atomically consumed once. The phone verification token is signed, short-lived, and bound to the normalized phone. Changing the phone in checkout clears the verified UI state. OTP verification is customer phone-control proof only; admin login remains separate.

Set all server-side variables together in Render: `WHATSAPP_PHONE_NUMBER_ID`, `WHATSAPP_BUSINESS_ACCOUNT_ID`, `WHATSAPP_ACCESS_TOKEN`, `WHATSAPP_OTP_TEMPLATE_NAME`, and `WHATSAPP_API_VERSION` (for example, a currently supported `vNN.0`). Meta's [official WhatsApp Cloud API collection](https://www.postman.com/meta/whatsapp-business-platform/documentation/wlk6lh4/whatsapp-cloud-api) describes the required WhatsApp Business Account and business phone setup. Approve a WhatsApp authentication template that matches the body and copy-code button components used by `server/src/services/whatsappService.js`. Meta template/account approval and credentials were not available here, so provider delivery was not verified. Incomplete configuration fails with a sanitized service error; the production app never returns the OTP. Mock `MESSAGING_PROVIDER` concerns order notifications only and does not simulate successful OTP verification.

Phone verification currently follows each restaurant's `phoneVerificationEnabled` policy and is required again in each guest checkout. There is no customer account model for durable verified-phone state, suspicious-activity history, or account recovery. Resend and verification rate limiting use IP counters plus database phone limits; Redis outage does not authorize a phone.
