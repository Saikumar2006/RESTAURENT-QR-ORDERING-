# Food payment gateway configuration

The existing online food-payment adapter supports Razorpay. Credentials are platform environment variables (`PAYMENT_PROVIDER`, `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, and `RAZORPAY_WEBHOOK_SECRET`), not restaurant-owned linked accounts. The new owner dashboard status card reports only provider availability and explicitly says linked restaurant accounts are not configured. It never returns credential values. Do not route merchant funds through a platform account without the provider's approved marketplace/linked-account arrangement and applicable compliance approval.

Production defaults to `unconfigured`; payment creation returns a service-unavailable error until Razorpay is configured. `PAYMENT_PROVIDER=mock` is allowed only outside production and its demo buttons render only in development. Render no longer sets the mock provider. Razorpay verification checks the HMAC signature and then fetches the payment server-side to match provider order, captured status, amount, and currency. The webhook checks its signature and payment/order amount/currency; updates are conditional on pending state. Repeated create-order calls reuse a pending provider attempt.

The existing browser checkout state is recoverable on refresh through the saved order ID/session token. Provider failures have a retry/status path. Marketplace sources are rejected by online payment initiation. Cash on delivery, merchant-entered paid confirmation, restaurant-specific credentials, provider switching, and refund workflows are not implemented. No payment sandbox or live charge was exercised.

Production configuration must be set in Render's encrypted environment settings only. Configure the provider webhook URL as `https://<service-host>/api/payments/webhook`, use the provider's sandbox first, and verify that only signed captured transactions change order payment state. Razorpay's [server integration guidance](https://razorpay.com/docs/payments/server-integration/python/integration-steps/) calls for server-created orders, server-side signature verification, and captured payment status checks; see also the [Payments API reference](https://github.com/razorpay/markdown-docs/blob/master/api/payments.md). Roll back by unsetting the provider and redeploying; the application safely disables new online payment attempts.
